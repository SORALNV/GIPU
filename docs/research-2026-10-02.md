## 進め方

1. 小ファイル大量、数KiB〜数MiBの独立ファイル、単一大ファイル、Stored／Deflate／空ファイル混在の比較用コーパスと再現可能な測定を用意する。
2. GPU StreamingのCPU CRC併用による二度読み削減、Gzip LOOKAHEAD、CPUの大ファイル・メモリ制御を実装・比較する。
3. 入力規模とCPU/GPU特性に合わせた自動選択・混在処理を設計する。
4. 小ファイルのZIP解析、ファイル生成、I/O重畳、メモリ・並列数の適応を詰める。
5. 正確性、メモリ上限、キャンセル、リソース不足、CLI互換性を検証し、実測と限界を記録する。

## 参照する一次資料

- [DEFLATE仕様 RFC 1951](https://www.rfc-editor.org/rfc/rfc1951): Huffman符号と32KiB履歴依存、ブロック境界。
- [nvCOMP C API](https://docs.nvidia.com/cuda/nvcomp/c_api.html)、[リリースノート](https://docs.nvidia.com/cuda/nvcomp/release_notes.html): 大きな単一Gzipバッファ向けLOOKAHEAD方式。
- [Rapidgzip論文](https://arxiv.org/abs/2308.08955)、[著者の実装](https://github.com/mxmlnkn/rapidgzip): 任意位置からの推測的ブロック探索、履歴解決、並列プリフェッチ。
- [libdeflate](https://github.com/ebiggers/libdeflate): 全バッファ解凍と高速CRC。Streaming APIは別の設計が必要。
- Linux man-pagesの[open(2)](https://man7.org/linux/man-pages/man2/open.2.html)と[link(2)](https://man7.org/linux/man-pages/man2/link.2.html): `O_TMPFILE`、名前なし出力の確定、`/proc/self/fd`経由のリンク。
- [openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html): BENEATH／NO_SYMLINKSによる相対パス全体の制約。安全性を保ちつつ短いsyscallを集約する。

工程1: 5時間の作業を開始。元リポジトリはclean、既存50GB ZIPを確認。新規の速度測定は同時実行を避け、CPU/GPU選択による改善と個別最適化を区別して記録する。

工程2: Streaming出力にCPU CRCを併用する変更と、比較用`--stream-crc gpu`を実装。CPU／libdeflate／GPU auto・stream・batchの5統合スイートが成功。使用不能なTMPDIRでもCPU CRCの検証が成功し、展開データの一時保存を不要にしたことを確認。固定seedの8種類のコーパスをOptane上へ生成し、基準バイナリとの比較を開始。

工程3: 初回7ケース×test/extract×3反復の比較が完了。小〜中規模と混在では16 worker CPUがGPUより速い。混在GPUではStored／空Deflateがバッチを分断している。LOOKAHEADを選択可能にし、実機の互換性・CRC・予算・出力保護テストに成功。ただし1GiBの高圧縮率テキストでは従来GPUバッチより遅く、既定には採用しない。並列CPUにホスト予算とStreaming切替を実装し256MiB制限を解消。CPU統合テストとASan／UBSanが成功。初回の生ログは`bench-results/corpus-initial-20261002.jsonl`、LOOKAHEAD／Streaming比較は`bench-results/corpus-lookahead-20261002.jsonl`へ逐次保存。

工程4: CPU Streamingへ任意のISA-L依存を組み込み、Rapidgzip 0.16.0（commit `d2350e9c9ba54398cd64e45bfc8c631beec017f0`、librapidarchive `1221a30bb548b305a69e5715f2bc348ba37ac243`）のヘッダ経路を追加。Rapidgzipは内部zlibを使う実験構成で、厳密なRSS上限は保証しない。ZIP解析の小さいpread集約・ASCII名・エラー文字列の成功時確保削減を実装し、中央ディレクトリ256MiB上限を追加。4種のCPU統合スイートと3種のCPU ASan／UBSanスイートが成功。長い追加フィールド／コメントによるキャッシュ境界、不正Deflate、途中切れ、末尾余剰データもテスト。GPU Streamingの8GiB反復測定は継続中で、CPU性能比較とは重ねない。

工程5: エントリ選択配列、CPU/GPU同時実行、片側エラーの停止伝播とjoin、GPU不在時のCPU切替を実装。GPU側にも固定化ホストメモリの予算を追加。CPU・hybrid・libdeflate・Rapidgzip・ISA-L・GPU4方式の9統合スイートに成功。8GiB単一の高圧縮率テキストでは、CPU zlibの実展開4.68秒に対しGPU Streamingは約73秒であり、GPUへの一律配送は不適切と確認。初期GPU方式の比較を完了し、ヘッダ軽量化／CPU方式／hybridの性能比較へ移った。

工程6: 極小32,768ファイルでは、改善前後の16 worker CPUでtest中央値0.1433→0.0265秒、実展開0.2430→0.1306秒。CPU単一大ファイルでは全量バッファよりISA-L Streaming＋高速CRCが速く、全量バッファの既定上限を64MiBへ変更。8GiB高圧縮テキストのISA-L経路はtest約0.97秒・実展開約2.16秒で、改善の大部分はzlib CRCから高速CPU CRCへの変更に由来する。高圧縮率ではRapidgzipのメモリ消費・速度が不利な例も確認した。

工程7: zlib／libdeflate／ISA-LのASan・UBSanビルドへそれぞれ2,010ケース、計6,030ケースのCPU変異試験を実施。全経路で72成功・1,938拒否、成功はzipfileと照合し、クラッシュ・タイムアウト・サニタイザ検出なし。異常入力全般の安全性を証明するものではない。`O_TMPFILE`と既存の名前付き出力の両方を実装・検証。GPUのStored／Streaming切替で固定化バッファを解放しすぎる回帰を発見し、固定12MiB予約の範囲で再利用するよう修正した。

工程8: KaggleのNPYバイナリ先頭8GiBから、単一エントリ・圧縮後6,426,188,962 bytesのZIP64を作成。元NPYは変更せず、ZIPは公開しない。初回実展開はISA-L15.95秒、Rapidgzip16 worker3.89秒、GPU Streaming33.84秒、GPU LOOKAHEAD43.70秒（実際に8GiBを1バッチ処理）。すべて出力全体SHA256一致。1回だけの暫定値であり、反復比較を追加する。既存50GB ZIPのtest初回はCPU16 worker12.82秒、GPU pipeline18.21秒、CPU/GPU50%分担14.28秒。50GB実展開の出力方式・分担比較を開始した。

工程9: 50GB実展開18回を完了。全件CRC／サイズと各回128件SHA256一致。継続書き込みで約42〜93秒の変動があり、CPUとGPUを同時に増やせば速いとはいえない。自動選択はCPUを既定とし、GPU・単一ストリーム内部並列は明示許可時だけ候補にする方針を実装した。GPU host slotを一体化し、入力は先頭・出力は末尾へ置く。次入力と前出力が重なる場合だけwriterをjoinし、異なるバッチの最大容量を別々に足す無駄を省いた。

工程10: GPU Streamingの大容量キャンセル試験で15秒以内に終了せず、GDBでcallbackの例外後にnvCOMP内部のthread joinが待ち続けることを確認。単にostream例外を抑える試行でも改善しなかった。通常CPUとRapidgzipはキャンセル後に一時出力を片付けて終了した。

工程11: GPU Streamingをposix_spawnした子へ分離。子はread-onlyのZIP FDとpipeだけを持ち、親がサイズ・CRC・出力ファイルを管理する。連続Streamingで子を再利用し、バッチへ移る前に破棄。親の停止時は自分の子だけを終了・回収し、親の強制終了はparent-death signalで子へ伝える。合成／実データ8GiBの停止は約0.11〜0.15秒へ改善、SIGINT／SIGTERMで一時出力なし、worker残留なし。子のSIGSTOPは無進捗timeout、SIGKILLはEOFエラーとして未検証出力を保護できた。10統合スイート、zlibのみの最小3スイート、修正版ISA-L静的リンク6スイートが成功。autoのASan／UBSan変異3,010件とRapidgzip修正版ISA-LのRelease変異3,010件も検出なし。262,144極小ファイル等、追加4コーパスを作成し次の反復測定へ移る。
